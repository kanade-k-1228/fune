# 航路データの更新（サブエージェント分割型）

`data/lines/<id>.yaml` を運航会社の公式情報源で確認して最新化するスキル。
**調査はサブエージェントに分割してファンアウト**し、本体（オーケストレータ）が結果を統合して編集・検証する。

データ仕様（スキーマ・flags・時刻形式・schedule DSL・検証ルール）は
**[`../REFERENCE.md`](../REFERENCE.md) を先に読むこと**。本文ではオーケストレーション手順に絞る。

## オーケストレーションの全体像

```
本体: 対象 YAML を読む → 調査タスクに分割
   ├─ サブエージェント#1 ── source[0] を調査（検索 / fetch / PDF・画像 DL & Read）→ 構造化所見
   ├─ サブエージェント#2 ── source[1] を調査 …                                    → 構造化所見
   └─ サブエージェント#N ── 「<航路名> 時刻表」を Web 検索で広く探索              → 構造化所見
本体: 所見を突き合わせて Edit → pnpm validate → 報告
```

- **調査サブエージェントは読み取り専用**（YAML を編集しない）。同一ファイルへの同時編集衝突を避けるため、編集は本体が一括で行う
- サブエージェントは独立に走らせる（Task/Agent ツールを 1 メッセージで複数同時起動するとファンアウトできる）

## フェーズ 1: 準備（本体）

1. `Read` で対象 YAML を読み、現在の `source` / `timetables` / `fare` / `notes` / `flags` / `schedule` を把握する
2. 調査タスクに分割する。基本は **source の URL ごとに 1 サブエージェント**。加えて、公式 URL が古い/死んでいそうなら「Web 検索で最新の公式時刻表を探す」サブエージェントを 1 つ足す
3. 各サブエージェントに「現在の YAML の関連部分」を渡し、何を検証してほしいかを明示する

## フェーズ 2: 調査（サブエージェントにファンアウト）

各調査サブエージェントへ渡すプロンプトの雛形:

```
あなたは「ふねたび！」航路データの調査担当。YAML は編集せず、所見を構造化して返すこと。

対象航路: <route>（運航: <name>） / 航路ID: <id>
調べる情報源: <URL または「<航路名> 時刻表 で Web 検索」>
現在の YAML（関連部分）:
  timetables: ...
  fare: ...
  notes: ...
  flags: ...
  schedule: ...
今日の日付: <YYYY-MM-DD>

手順:
1. WebFetch（HTML 解析）または WebSearch（「<航路名> 時刻表」「<運航会社名> 公式」）で当たる
2. ページ内に時刻表 PDF / 画像へのリンクがあれば必ず追跡する
3. PDF / 画像は次の手順でローカルに落として Read で読む（Read は PDF を document、画像を image として読み取れる）:
     Bash: mkdir -p /tmp/funatabi-update/<id>/
     Bash: curl -sL "<url>" -o /tmp/funatabi-update/<id>/<file>
     Read: /tmp/funatabi-update/<id>/<file>
4. 信頼するのは公式（運航会社・自治体・観光協会の公式サイト）のみ。SNS / ブログ / まとめは参考程度で source には入れない
5. 現在の YAML と最新情報を比較し、差分を所見として返す

返す内容（この形式で）:
## 所見
- timetables: 便ごとの最新時刻（dia 名・便名・stops 配列。null=通過 / "HH:MM" / ["着","発"]）
- fare: 最新運賃（改定日が分かれば添える）
- notes: 運休・特記の変更
- flags: 追加/削除すべきもの（suspend/seasonal 等）
- schedule: 適用ダイヤ・臨時運行/運休の変更
- 改廃/休止の有無
## 確認した情報源（公式かどうかを明記）
- <URL>（公式 / 参考）
## 確信度
- high / medium / low（一次情報の鮮度・明瞭さで判断）
差分が無ければ「変更なし」、URL がアクセス不能なら「確認不能（理由）」と返す。
```

ポイント:
- **PDF / 画像が読める環境**であることを前提に、必ず DL → Read させる（リンクのテキストだけで判断しない）
- 各サブエージェントは `WebSearch` `WebFetch` `Bash`(curl) `Read` を使う。`Read` が PDF/画像をそのまま LLM に渡す
- 調査担当に `Edit` / `Write` はさせない

## フェーズ 3: 統合・編集（本体）

1. 各サブエージェントの所見を突き合わせる。**確信度・情報源の鮮度**で採否を決め、矛盾は公式の一次情報（PDF/公式ページ）を優先する
2. 差分があるものだけ本体が `Edit` で書き換える:
   - `timetables.<dia>.voyages[].stops` の時刻
   - `schedule` / voyage の `schedule`（適用ダイヤ・臨時運行/運休）
   - `fare`（運賃改定。「(2026年4月改定)」等を添える）
   - `notes`（運休情報・特記事項）
   - `flags`（`suspend` / `seasonal` の追加・削除）
   - `source`（公式 URL が変わっていた場合のみ追加）
3. 休止なら `suspend` を `flags` に追加し、`notes` に時期・理由を書く。廃止が確認できた航路はファイルごと削除する
4. 編集後に必ず `pnpm validate` を実行し、合格を確認する

## 守ること（検証で弾かれる）

- `ports` の港 ID 集合は**変更しない**（港の追加・削除は `add-port` / `add-line`）
- `coords`（航跡座標）は**触らない**
- 各 voyage の `stops` 配列長は航路トップの `stops` 長と一致
- `flags` / 時刻形式 / `schedule` の条件キーは REFERENCE.md の許容値のみ
- スキーマは `.strict()`。**未定義キーを足さない**
- 確信が持てない情報は書かない。差分が無ければ何も変えない

## 報告フォーマット

```
## 変更まとめ
- timetables.normal.voyages[2].stops: ["09:30","11:30"] → ["09:45","11:45"]
- fare に「2026年4月改定: 大人600円」を追記
- flags に seasonal を追加

## サブエージェント所見の採否
- #1 source[0] PDF（確信度 high）→ 採用
- #2 Web 検索（確信度 low / 個人サイト）→ 不採用

## 確認した情報源
- https://example.com/timetable-2026.pdf (公式 PDF 時刻表)

## validate
- pnpm validate: ✓
```

差分なし / 確認不能のときは、その旨を一行で報告して終了する。

## 複数航路を一括更新したい場合

複数航路をまとめて更新するときは、**航路ごとに 1 サブエージェント**を割り当てる。
別ファイルなので編集衝突が起きず、各サブエージェントが「調査 → Edit → 自分の担当ファイルだけ検証」まで完結できる。
本体は最後に全体を `pnpm validate` し、各担当の報告を束ねる。

非対話の大量バッチには、このスキルに同梱の Claude Agent SDK ランナー
`update.ts`（リポジトリルートで `pnpm update [--id <line-id>] [--limit N]`、要 `CLAUDE_CODE_OAUTH_TOKEN`）を使う。
ランナーの単体エージェント用システムプロンプトは同ディレクトリの `batch-prompt.md`。
本スキル（対話・サブエージェント分割）とバッチランナーは同じ更新ポリシー（REFERENCE.md）を共有する。

### このスキルに同梱のファイル

- `SKILL.md` — 対話的・サブエージェント分割型の更新手順（このファイル）
- `update.ts` — バッチランナー（`pnpm update`）
- `batch-prompt.md` — バッチランナーの単体エージェント用システムプロンプト
- 実行時に `state.json` / `logs/` を生成（gitignore 済み）
